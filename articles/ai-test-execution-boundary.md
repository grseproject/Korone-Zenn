## 🧭 課題：ルールを知らないまま動いて「できない」と返す

実行の指示を出すと、Codexがディレクトリのルールを無視して動き、最終的に「実行できない」という結果を返してきました。

原因は、Codexがそのルールを知らなかったことでした。この問題は、Sol 6を使って解決しました。原因の分析も、この記事のもとになったレポートの作成も、Sol 6で行っています。

整理してみると、AIエージェントは次のような手がかりを組み合わせて、「今どこで作業しているか」「誰が実行するのか」を判断しています。

- フォルダ名
- 設定ファイル
- 役割名
- 自然言語の指示

そのため、同じ言葉が複数の意味で使われていると、次のような勘違いが起こりえます。

- 案件ごとの保存先を、独立した実行環境として扱う
- 実行制御の役割と対話の役割が、同じツールを同時に使う
- 内部で完結する処理を、別の役割への指示や中継が必要な処理だと解釈する
- ツールが使用中なだけの状態を、セットアップ未完了と判断する

### 用語の衝突

特に問題になりやすいのが、次のような言葉です。

| 用語 | 想定していた意味 | 誤解される可能性がある意味 |
|---|---|---|
| Workspace | 案件別の結果保存先 | AIエージェントの作業ディレクトリ |
| Agent | 実行制御を担当する定義済みの役割 | 対話中のAI全体、または任意の作業者 |
| Project | 案件別の実行記録 | 独立したソフトウェアプロジェクト |
| 渡す・割り振る | 定義済みフロー内の処理 | 対話役が別の役割へ追加指示を送る操作 |
| Setup | ツール導入とログイン完了 | 一時的なセッション競合を含む実行可否全般 |

### フォルダの形が「作業場所」に見えてしまう

案件ごとのフォルダに、設定・入力・出力・ナレッジ・テスト資産が揃っていると、形だけを見ると独立した作業環境に見えます。そこに説明文でも「Workspace」と書いていると、AIはそのフォルダに移動して作業を始める判断をしやすくなります。

## 💡 解決策：実行環境と案件記録を分ける

対策の中心は、**実行環境と案件記録を「構造」「名前」「設定」の3つで分けること**です。あわせて、ブラウザーや端末のように状態を持つツールは、使う役割を1つに限定します。

### フォルダ構成

作業を始める場所（実行制御ルート）を1つに固定し、案件ごとのフォルダはその下に「記録の保存先」として置きます。

```text
execution-system/
├── operating-rules.md
├── control-definitions/
│   └── test-execution-controller.conf
├── workflow-skills/
│   └── software-testing/
├── operation-guides/
├── execution-records/
│   ├── index.md
│   └── <record-key>/
│       ├── record-manifest.md
│       ├── config/
│       ├── templates/
│       ├── input/
│       ├── output/
│       ├── knowledge/
│       └── tests/
└── migration-history/
```

- `execution-system/`：AIエージェントが作業を始める唯一の場所。役割定義、ワークフロー、実行ガイド、案件の索引を置く
- `execution-records/<record-key>/`：案件ごとの設定、入力、結果、証跡、再利用する資産を置く場所。作業ディレクトリ、役割定義やワークフローの探索先、認証情報やブラウザー状態の保存先には使わない

### 記録フォルダに「これは記録です」と書いておく

各案件の記録フォルダには、機械的に判定できるマニフェストを置きます。

```yaml
kind: execution_record
record_key: <record-key>
controller: test-execution-controller
```

`kind` を明示しておくことで、フォルダの形だけを見て「独立した実行環境だ」と判断される可能性を下げます。

### 用語を置き換える

| 避けたい表現 | 推奨する表現 |
|---|---|
| PJ Workspace | PJ execution record / 案件実行記録 |
| Workspace root | execution control root / 実行制御ルート |
| Project folder | record root / 記録ルート |
| Agentへ渡す | 定義済み制御フローが処理する |
| Setup blocked | setup unavailable / session busy / precondition unavailable に分ける |

用語は置き換えるだけでは足りず、フォルダ名、設定ファイル名、役割定義、運用ガイドのすべてで同じ言葉を使う必要があります。

## 🛠️ 具体的な実装方法：実行の所有者と状態の分類

### 状態を持つツールは、実行制御役だけが使う

| 操作 | 担当 | ほかの役割の扱い |
|---|---|---|
| 対象案件の特定 | 実行制御役 | 結果を見るだけ |
| 実行するケースの選定 | 実行制御役 | 選定を解釈し直さない |
| ブラウザー・端末の操作 | 実行制御役 | 同時に使わない |
| 実行結果の保存 | 実行制御役 | 同じ記録を上書きしない |
| 外部システムへの反映 | 実行制御役 | 承認条件を満たした場合だけ実施 |
| ユーザーへの最終報告 | 対話役または実行制御役 | 報告が重ならないようにする |

対話役は、実行制御役への指示の中継や、実行判断の言い換えをしません。フローが始まったあとは、完了・承認待ち・停止理由を見守る立場になります。

### 「できない」を1種類にしない

「実行できない」をひとまとめにせず、少なくとも次のように分けます。

| 状態 | 意味 |
|---|---|
| setup unavailable | 必要なツールや接続設定が存在しない |
| authentication required | ユーザーのログインが必要 |
| session busy | 別の正規の所有者が同じセッションを使用中 |
| precondition unavailable | テストケースの事前条件を用意できない |
| execution failed | 実行は始めたが、操作または検証に失敗した |

特に、`session busy` を `setup unavailable` として記録しないことが大事なポイントです。

:::details 実行制御ルートと案件記録のルール
**実行制御ルート**
- 作業ディレクトリを実行制御ルートから変えない
- 案件キーは1つの索引から特定する
- 登録されていない、またはあいまいな案件キーを推測しない
- 実行制御役以外は、状態を持つツールを使わない
- 案件記録の中に、役割定義やワークフローを置かない

**案件記録**
- `record-manifest.md` で記録の種類を宣言する
- 実行結果と証跡は案件記録の中に保存する
- 認証情報、Cookie、セッション状態、APIキーを保存しない
- 外部向けのコメントに端末のパスを書かない
- 画像を参照するときは、管理されたファイル名だけを使う
:::

:::details 移行手順（9ステップ）
1. 今の実行ルートと、案件ごとの保存先を特定する
2. 案件ごとの保存先を `execution-records/` の下に移す
3. 各案件に `record-manifest.md` を追加する
4. 案件ごとの `workspace` というファイル名や説明を `record` に変える
5. 実行制御の定義に、作業ルートの固定とツールの所有権を追加する
6. ワークフローに管理実行モードを追加し、通常のWorkspace探索を無効にする
7. 古いパスを参照している索引と、保存済みの記録を機械的に更新する
8. 古い用語と古いパスが、有効な設定に残っていないことを確認する
9. 構造の変更履歴を作り、変更理由と互換性の対応を記録する
:::

## 🎯 効果：期待していること

この構成で期待している効果は次のとおりです。

- 作業ディレクトリの勘違いを防ぐ
- 実行する役割が重ならないようにする
- ブラウザー・端末のセッションの取り合いを防ぐ
- 「環境の不備」と「一時的な使用中」を区別できるようにする
- 案件記録の保存先と実行環境を分ける
- 新しい案件を追加するときの運用をそろえる
- 問題が起きたときに、どこの責任範囲かを分かりやすくする

ただし、フォルダ構成だけでは、状態を持つツールの取り合いを完全には防げません。役割定義や実行時の制御でも、同時利用を禁止するか、排他制御をする必要があります。

## 📝 まとめ

もう一つ気をつけたいのが、否定の書き方です。AIエージェントは、否定の表現だけだと見落とす可能性があります。

* ❌ 「案件記録はWorkspaceではない」とだけ書く
* ✅ **「実行制御ルートはここ」「ブラウザーの所有者はこの役割」と、肯定の定義も一緒に書く**

今回感じたのは、今までなんとなく動いていた内容が、モデルの進化によって修正が必要になった、ということでした。
